# 17. 연간 예산 배분과 항목별 저장

2026-10-06. 16 문서의 다음 단계였던 연간 예산 통제와 조직 JSON 저장 분리를 구현했다. 전체 제품 요구사항의 완료 선언은 아니다.

## 사용 흐름

1. **연간 계획 → 프로젝트·예산 → 프로젝트별 배분**에서 해당 연도에 진행하는 사업에 금액을 나눈다. 전체 사업비가 여러 해에 반복 배정되는 것을 막는다.
2. 배정 합계는 연간 예산 이내, 한 프로젝트의 여러 연도 배정 합계는 사업 전체 예산 이내여야 한다. 여러 사업의 재배분을 한 번에 저장하고 담당자·시각·사유·이전 금액을 남긴다.
3. 예정·검토 중 요청은 입력할 수 있으며 예정까지 합친 부족액을 안내한다. **승인 시** 사업 전체·세목 예산과 해당 연도 배정액을 모두 검사한다. 이미 승인한 금액보다 배정액을 줄일 수 없다.
4. 기간 보고서의 화면·HTML·DOCX·XLSX에 해당 연도 배정액과 미배분액을 담는다. 이전 보고서는 당시 집계 기준과 수치를 유지한다.

기존 계획에 예산 규칙을 소급해서 강제하지 않는다. 관리자가 **배분 적용**을 누른 계획부터 `budgetPolicy=yearly`가 된다. 적용하지 않은 계획은 기존 사업 전체 예산을 표시한다. 새 계획도 먼저 배분을 적용해야 한다.

집행 한도는 **집행일의 연도**, 현금 지급 집계는 **실제 지급일** 기준이다. 적용된 연간 계획을 마감하면 해당 연도의 집행 및 지급 수정도 잠근다. 먼저 계획을 다시 열어야 한다. 현금 이월·보조금 정산 규정·다단계 결재·실제 송금 기능은 아니다. 연간 관리와 배분 변경은 조직 대표·관리자 권한이다.

## 저장 구조와 조회

- `value_lens` 전용 스키마의 14개 `workspace_*` 테이블에 프로젝트·업무·문서·집행·지표·실적·보고서·활동·연간 계획/배분 등을 **항목별 행**으로 저장한다. 중첩 버전·지급·이력은 항목 내부 JSONB로 유지한다. 모든 필드를 완전히 관계형 정규화한 구조는 아니다.
- 조직 행은 설정과 버전 번호만 가진다. 변경한 항목만 일괄 INSERT/UPDATE/DELETE하며, 조직 버전 검사·작업 영수증·앱 알림과 같은 트랜잭션으로 저장한다. 이번 트랜잭션에서 새로 발급한 저장 토큰을 함께 검사하므로, 늦게 도착한 동일 요청이 기존 작업 영수증으로 최신 값을 덮어쓸 수 없다.
- 기존 `storage_version=1` 조직은 읽을 때 그대로 유지한다. 첫 성공한 업무 저장에서 기존 JSON을 수정/삭제할 수 없는 `workspace_checkpoints`에 보관하고 항목을 옮긴다. 새 조직은 처음부터 버전 2다. 원본 파일은 기존 비공개 Storage에 그대로 남는다.
- **조직 JSON 1MiB 저장 제한을 제거**했다. 단일 항목은 2,000,000바이트까지다. 큰 보고서나 문서 이력은 기간/자료를 나눠야 한다.
- 화면 응답이 1,500,000바이트를 넘으면 자료 목록을 나눠 조회한다. 한 페이지 최대 500개, 약 1MB를 기준으로 묶되 단일 항목은 2MB까지 허용한다. 클라이언트는 3개 요청까지 병렬로 처리한다. 조직/프로젝트 권한을 각 페이지에서 확인한다.
- 모든 페이지의 버전이 같을 때만 화면에 반영한다. 중간에 자료가 변경되면 최신 작업실을 한 번 다시 조회한다. 저장 명령 자체를 재전송하지 않는다. 두 번째 충돌이나 오류는 사용자에게 알리며 부분 자료로 화면을 덮어쓰지 않는다.
- API의 명령 검증과 초기 목록 생성은 아직 조직 전체 상태를 메모리에서 조립한다. 동시 쓰기도 기존 조직 버전 기준 충돌 검사를 유지한다. 화면별 서버 조회·독립 항목 충돌 병합·검색 인덱스·가상 목록·장기 보관 정책은 후속 범위다. 무제한 규모나 공동 편집 구현을 뜻하지 않는다.

## 전환과 복구

마이그레이션 `20261006084727_workspace_row_storage.sql`은 운영 Supabase에 적용했고 앱 마이그레이션 이력에도 LF 기준 SHA256 `273a53296fd0e575e3886e30b1894cb3534a43ed52767103f459bce80c874694`를 기록했다. 새 환경변수는 없다. 다른 앱 스키마와 공유 Auth 설정은 변경하지 않았다.

DB 마이그레이션은 기존 조직을 즉시 전환하지 않으므로 이전 서버와 함께 먼저 배포할 수 있다. 그러나 버전 2로 전환된 뒤에는 **이전 서버 버전만 바로 배포해서는 안 된다**. 긴급 복구는 서비스 쓰기를 멈춘 뒤 운영자가 다음 절차를 따른다.

```sh
# 기본은 읽기 점검. 조직 ID와 크기·호환 여부만 표시한다.
npm run db:workspace-compat -- --org ORGANIZATION_ID
# 점검한 해당 조직을 이전 표현으로 변환할 때만 명시적으로 실행한다.
npm run db:workspace-compat -- --org ORGANIZATION_ID --apply
```

명령은 최신 항목들을 합친 JSON과 버전 증가를 원자적으로 저장한다. 최초 체크포인트로 덮어쓰지 않는다. 이전 서버는 조직당 1MiB 제한이 있으므로 그보다 큰 조직은 변환을 거절하며 새 버전에서 전진 수정해야 한다. 전체 DB/Storage 재해 복구, 외부 백업 보관, 운영자 복구 훈련은 별도 과제다.

## 확인한 범위

- 전체 자동 테스트 **122/122**, 타입 검사 통과. 연간/사업/세목 한도, 동시 승인, 권한, 보고 스냅샷, 체크포인트·전환·최신 데이터 복원, 요청 재시도와 분할 조회 버전 일관성을 포함한다.
- 합성 1년 자료: 업무 5,000건·현장 기록 365건·연결 문서 365건·보고서 52건, JSON **5,856,317바이트**. 1MiB 이후에도 저장하고 모두 복원했다. 조회 15회, 최대 응답 906,291바이트. PGlite 테스트이며 운영 부하 보장 수치가 아니다.
- 실제 Supabase 서버 역할로 합성 업무 5,000건, 약 **6.2MB**를 한 트랜잭션 안에서 저장·복원했다. 당시 삽입 약 725ms, 재조립/수신 약 709ms. 전부 롤백했고 잔여 조직 0건을 확인했다. 실제 조직 데이터를 변경하거나 최종 사용자 지연을 측정한 검증은 아니다.
- 실제 React·서버·PGlite 및 합성 사용자로 약 2MB 작업실을 분할 조회해 연간 배분→초과 승인 거절→재배분→승인→기간 보고서를 검증했다. 업무 2,600건 보존, 화면 오류 0, 390px 모바일 문서와 364px 대화상자 가로 넘침 0. 모바일 표는 표 안에서 가로 스크롤한다.
- 새 테이블 15개(항목 14 + 체크포인트)의 RLS와 브라우저 역할 직접 조회 차단을 확인했다. 재조립 함수는 SECURITY INVOKER이며 서버 역할만 실행할 수 있다. 체크포인트의 UPDATE 권한도 없다.
- Advisor의 기존 공유 프로젝트 항목은 그대로다: [RLS 무정책 정보](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy), [비밀번호 유출 방지 경고](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection), [기존 FK 인덱스 정보](https://supabase.com/docs/guides/database/database-linter?lint=0001_unindexed_foreign_keys). 새 테이블에서는 [아직 사용 이력이 없는 인덱스 정보](https://supabase.com/docs/guides/database/database-linter?lint=0005_unused_index) 외 새 권한 문제는 없었다.
