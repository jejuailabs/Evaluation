# 18. 미분류 자료함과 반복 업무

2026-10-06. 17 문서에서 남긴 자료 수집과 정기 업무를 기존 조직·프로젝트·평가 흐름에 연결했다. 전체 제품의 완료 선언은 아니다.

## 먼저 모으고 나중에 연결

- **자료함 → 미분류 자료함**에서 프로젝트 없이 파일 또는 자유 메모를 보관한다. 사진·녹음·엑셀·HWPX 등 파일 형식을 제한하지 않으며, 파일당 25MB·한 번에 12개·기존 조직 저장 한도 500MB를 유지한다. 메모는 10,000자까지다. 녹음은 원본 보관이며 STT 기능은 아니다.
- 원본 이름·크기·업로더·시각은 서버가 확정한다. 부분 실패 시 저장한 파일은 건너뛰고 실패한 파일만 재시도한다. 완료 전 업로드 예약도 기존 저장 한도 계산에 포함한다.
- 미분류·보관 상태의 자료는 **올린 구성원과 조직 대표/관리자만** 조회한다. 일반 구성원은 본인 자료만 분류·보관·복원할 수 있다. 읽기 전용 구성원은 변경할 수 없다.
- **프로젝트 연결**은 활성 프로젝트 참여 권한이 필요하다. 관리자는 조직 전체에서 분류할 수 있다. 연결 후에는 해당 프로젝트의 권한을 따르므로, 업로더여도 프로젝트에 참여하지 않으면 더 이상 볼 수 없다. 전체 응답·분할 조회·원본 다운로드에 같은 규칙을 적용한다.
- 연결 시 기존 파일 ID·원본·등록 이력을 유지한다. Storage 파일을 다시 올리거나 복사하지 않는다. 파일의 프로젝트 귀속, 문서 생성, 선택적인 활동 기록, 분류 이력, 조직 버전 변경을 한 트랜잭션에서 저장한다. 충돌 시 모두 취소하며, 오래된 요청으로 원본의 귀속만 뒤집을 수 없다.
- **현장 기록도 함께 남기기**로 날짜·내용·업무·목표를 연결할 수 있다. 이 기록은 기존 활동 화면과 프로젝트 보고에 포함된다. 실적 수치는 기존 성과 화면에서 제안·검토·확인해야 집계된다. 자료를 분류했다는 이유만으로 성과가 확정되지 않는다.
- 보관은 삭제가 아니다. 원본과 보관·복원 이유를 유지하며 저장 용량도 유지한다. 잘못 분류된 문서의 프로젝트 이동·병합·영구 삭제는 이번 범위에 포함하지 않는다.

## 정기 업무를 미리 배정

- **프로젝트 → 업무·일정 → 반복 업무 만들기**에서 관리자에게 일/주/월 단위, 1~12 간격, 시작/종료일, 담당자, 우선순위, 메모, 연결 목표를 제공한다.
- 선택 기간의 실제 업무를 한 번에 생성한다. 최대 400회이며 프로젝트 기간 안이어야 한다. 주 반복은 시작 요일, 월 반복은 최초 날짜를 유지한다. 31일이 없는 달에는 말일을 사용하고 다음 달에는 다시 31일을 사용한다. 윤년을 처리한다.
- 생성한 업무는 기존 조직 보드·월간 캘린더·프로젝트 목록·목표 연결·댓글을 그대로 사용한다. 재전송한 동일 요청으로 일정이 중복 생성되지 않는다. 담당자에게는 회차 수만큼이 아닌 요약 알림 한 건을 보낸다.
- **앞으로의 일정 수정/반복 중단**은 적용일 이후의 예정 업무에만 적용한다. 적용일은 오늘 이후이며 반복 종료일까지다. 진행 중·완료·지난 업무와 개별 댓글을 보존한다. 변경자·시각·사유·이전 설정을 남긴다. 기존 반복의 주기/기간 변경이나 종료일 이후 자동 연장은 지원하지 않는다. 새 기간은 새 반복으로 만든다.
- 중단한 회차는 삭제하지 않는다. 이력을 펼쳐 볼 수 있고, 업무 진행 목록·완료율·프로젝트 마감 검사·기간/연간 보고의 업무 수에서는 제외한다. 이미 저장한 보고서는 당시 스냅샷을 유지한다.
- 일반 구성원은 기존 권한 안에서 개별 업무를 진행·완료한다. 반복 전체의 생성/일괄 수정/중단은 관리자 권한이다. 담당자는 활성 상태이며 그 프로젝트에 참여한 구성원이어야 한다.

## 저장과 배포

- `workspace_task_series`, `workspace_intake_items`를 추가해 항목 저장 컬렉션은 16개가 됐다. `files`·`file_uploads`의 프로젝트 참조만 미분류 동안 NULL을 허용한다.
- `20261006103556_intake_and_recurring_tasks.sql`을 운영 Supabase 전용 `value_lens` 스키마에 적용했다. LF 기준 SHA256: `359b6dcf3a3278165859f4b733fe0dcd1781a47769ef61bc72d29e2d3d718184`. 앱 마이그레이션 이력도 같은 트랜잭션에 기록했다.
- 새 테이블은 RLS를 켜고 서버 전용 역할만 허용한다. `anon`·`authenticated` 직접 조회 권한은 없으며 `read_workspace`는 SECURITY INVOKER다. 기존 Auth·SMTP 설정과 다른 앱 스키마는 변경하지 않았다. 새 환경변수는 필요 없다.
- 이전 조직은 기존 첫 저장 시 전환 정책을 유지한다. 17 문서의 항목당 크기 제한·전체 상태 조립·조직 단위 충돌 검사도 계속 적용된다.

## 검증

- 전체 자동 검사 **127/127**, 타입 검사 통과. 월말·윤년·회차 제한, 완료/진행 이력 보존, 중단 회차의 집계 제외, 분류 실패 롤백, 업로더 격리, 페이지별 조회 권한, 분류 후 원본 권한 이전, 동시 분류, 반복 알림/중복 요청을 포함한다.
- 실제 React 화면과 서버 API·PostgreSQL 호환 PGlite, 합성 계정으로 프로젝트 없는 메모/파일 업로드 → 프로젝트 생성 → 자료·활동 연결 → 반복 생성/완료/수정/중단 → 새로고침 후 이력 보존을 확인했다. 화면 오류 0, 390px 모바일 가로 넘침 0. 업무 표는 표 안에서 가로 스크롤한다.
- 실제 Supabase 서버 역할에서 합성 자료함 1건·반복 1건·업무 3건을 저장/재조립했다. 전부 롤백하고 잔여 조직 0건을 확인했다. 실제 고객 조직의 데이터를 변경한 인수 검사는 아니다.
- 새 테이블의 Advisor 항목은 미사용 인덱스 정보뿐이다. 공유 프로젝트의 기존 RLS 무정책 정보·유출 비밀번호 방지 경고·일부 FK 인덱스/기본키 정보는 이번에 변경하지 않았다.
