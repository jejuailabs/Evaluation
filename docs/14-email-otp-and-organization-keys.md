# 14. 이메일 인증번호·조직 가입키

2026-10-06. 전체 점검에서 확인한 가입·조직 참여와 모바일 보고서 문제를 보완했다. 나머지 AI·협업·저장 구조의 미구현 항목은 13 문서에 남아 있다.

## 사용자 흐름

1. 누구나 개인 이메일을 입력하고 인증메일을 요청한다. 조직 소속·초대 여부는 가입 조건이 아니다.
2. 메일의 숫자 인증번호를 화면에 입력하면 로그인된다. 틀린 번호·만료·재사용은 거부한다. 기존 이메일 링크와 Google 로그인도 유지한다.
3. 로그인 후 새 조직을 만들거나, 관리자가 전달한 `VL-XXXX-XXXX-XXXX-XXXX` 가입키로 참여한다. 특정 이메일에 묶인 기존 초대 링크도 사용할 수 있다.
4. 가입키로 참여하면 조직원 또는 읽기 전용 권한을 받는다. 조직 전체 프로젝트에 자동 접근하지 않으며 관리자가 배정해야 한다.

## 조직 관리자

- 조직 관리 → 조직 가입키에서 역할(조직원/읽기 전용), 유효 기간(1·7·30일), 인원 한도(1~1,000명)를 정해 발급한다.
- 새 키를 발급하면 기존 키를 폐기한다. 기존 구성원 소속은 유지한다. 별도 폐기 버튼도 제공한다.
- 키 원문은 발급 직후 한 번 표시한다. 서버에는 SHA-256 해시만 저장한다. 목록에는 사용 인원·만료·폐기 상태만 표시한다.
- 관리자/대표 권한은 키로 발급하지 않는다. 이용 중지된 구성원이 키로 상태를 되돌릴 수도 없다.
- 검증 요청은 인증된 계정별 10분에 10회로 제한한다. 인원 한도·조직 상태·폐기·만료는 가입 트랜잭션 안에서 재확인한다. 중복 요청으로 소속이나 사용 횟수가 중복 생성되지 않는다.

## 저장·인증

- 마이그레이션: `supabase/migrations/20261006052013_organization_join_keys.sql`.
- 전용 스키마의 `organization_join_keys`, `join_key_attempts` 두 테이블. RLS 활성, 서버 역할만 접근, 익명 직접 조회 불가. 기존 자료를 이관하거나 삭제하지 않는다.
- OTP 검증은 서버에서 Supabase 공식 `verifyOtp({email,token,type:'email'})` 호출 → 확인된 사용자 검사 → HttpOnly 세션 쿠키 발급 순서다. 토큰을 브라우저 JSON에 반환하지 않는다.
- 인증번호는 Supabase에서 발급·만료·재사용을 관리한다. 메일 템플릿은 `{{ .Token }}`과 기존 `{{ .ConfirmationURL }}`을 함께 사용한다.
- 공유 Supabase의 다른 서비스 메일은 그대로 두며 가치 돋보기 운영 callback에만 한국어 제목·본문·번호를 적용한다.

## 검증과 남은 범위

- 전체 테스트 **100개**, 타입 검사 통과. OTP·CSRF·잘못된 번호·재사용·가입키 만료/폐기/인원/중지/권한/요청 제한 포함.
- 두 개의 새 브라우저에서 OTP 입력→조직 키로 참여→대표가 구성원 확인까지 통과. 이 검증은 외부 Auth의 가상 응답과 실제 SDK·서버 API·PGlite를 사용했고 운영 회원을 만들거나 실제 메일을 보내지 않았다.
- 모바일 보고서의 390px 화면 가로 넘침을 수정하고 생성된 보고서에서 확인했다.
- 실제 운영 사용자의 인증번호 수신·입력과 Google 최종 동의·복귀는 별도의 사용자 인수 범위다. 전체 관리자 계정 지정, 현장 자료 AI 실적 추출, 실시간 협업, 저장 구조 분리, 기관별 출력은 이번 구현 범위가 아니다.
