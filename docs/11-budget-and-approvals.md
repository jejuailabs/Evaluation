# 예산 배정부터 요청·검토·지급·보고까지

2026-10-06 · v0.5. 기존 연간 운영과 문서 기반 지표 설계를 유지하며, 실제 공동 업무 중 빠져 있던 예산 처리 흐름을 확장했습니다.

## 연결한 사용 흐름

프로젝트 예산 → 재원·세목 배정 → 담당자의 지출 예정 작성 → 증빙 연결 → 검토 요청 → 관리자의 승인 또는 보완 요청 → 수정·재요청 → 한 번 또는 여러 번 지급 기록 → 기간 보고서·Excel 원장.

화면은 프로젝트의 **예산** 한곳에 모았습니다. `집행 내역`과 `예산 배정`으로 나누고, 개별 요청의 상세 화면에서 현재 상태에 맞는 처리만 제공합니다. 홈에는 관리자가 검토하거나 지급할 요청, 일반 담당자가 보완할 요청이 나타납니다. 이메일·푸시를 보내는 알림은 아닙니다.

## 실제 구현과 규칙

| 구간 | 구현 |
|---|---|
| 세목 배정 | 재원 이름·세목 이름·배정액, 변경 사유와 이전 배정 보존. 세목 합계는 프로젝트 예산 이내 |
| 요청 | 제목·금액·집행일·담당자·목적·세목·원본 버전. 세목을 아직 나누지 않아도 미분류로 시작 가능 |
| 검토 | 예정/보완 → 검토 요청 → 승인/보완. 검토 의견 필수, 근거 원본 내려받기 |
| 수정·취소 | 예정/보완 중 내용 수정과 이전 내용 보존. 미지급 요청 취소 시 예산 예약 해제. 지급이 남아 있으면 취소 거부 |
| 지급 | 승인된 지출에 지급액·실제 지급일·메모·증빙 버전 기록. 부분 지급·잔액 표시, 초과·중복 지급 차단 |
| 입력 정정 | 잘못 입력한 지급을 무효로 표시하고 사유·담당자·시각 보존. 원장 삭제 없이 새 지급을 기록 |
| 예산 검증 | 승인액이 프로젝트/해당 세목 배정액을 넘으면 거부. 배정 축소도 이미 승인한 집행보다 낮출 수 없음 |
| 마감 | 미정리 요청이나 미지급이 남으면 프로젝트 완료 거부. 기존 업무·실적 검토·보고서 조건도 유지 |
| 보고 | 보고 당시 집행·지급·미지급과 처리 이력을 스냅샷으로 저장. 이후 수정이 기존 보고서를 바꾸지 않음 |

예정·검토·보완 중인 요청은 사용 가능한 예산에서 예약액으로 차감하지만 승인 집행으로 합산하지 않습니다. 예약 합계가 예산을 초과하면 표시하며, 실제 승인 시에는 다른 승인액을 포함해 배정 한도를 검사합니다. 미분류 집행도 프로젝트 전체 한도에 포함됩니다. 재원 이름은 분류용이며 특정 보조금 규정을 자동 판정하는 기능은 아닙니다.

## 지급일과 집행일의 구분

- **집행**은 요청에 기록한 집행일에 승인 금액을 반영합니다. **지급**은 개별 지급일의 실제 기록 금액을 반영합니다.
- 9월 집행 60만 원 중 10월에 20만 원을 지급했다면, 10월 보고에는 집행 0원·지급 20만 원으로 표시합니다.
- 미지급과 사용 가능액은 프로젝트 시작부터 보고 종료일까지의 잔액입니다. 기간 내 집행과 지급은 서로 다른 흐름이므로 둘을 단순 차감해 미지급을 만들지 않습니다.
- 명세에는 선택 기간의 집행·지급뿐 아니라 보고 종료일까지 남은 미지급도 포함합니다.
- 확인/취소/정정 상태는 보고 생성 당시 기준입니다. 과거 특정 날짜 당시의 승인 상태를 시간 순서대로 재구성하는 회계 원장은 아닙니다.
- 현재 집행일·지급일은 프로젝트 기간 안에서 기록합니다. 기간이 지난 뒤 정산하려면 진행 상태를 유지하고 사업 기간을 조정해야 합니다. 별도 정산 기간과 회계연도 이월은 후속 개발 대상입니다.

## 권한과 데이터 보존

조직 대표/관리자만 세목 배정·승인·지급·지급 정정을 할 수 있습니다. 일반 구성원은 배정된 프로젝트에서 본인이 담당한 요청을 작성·수정·요청·취소할 수 있습니다. 승인한 요청의 취소는 관리자만 가능합니다. 조회자는 쓰기를 할 수 없습니다. 미배정 프로젝트의 세목·요청·보고서는 내려보내지 않습니다.

이 단계는 **관리자 1단계 검토**입니다. 관리자 자신의 요청도 스스로 검토할 수 있습니다. 다단계 결재선·대리 결재·이해관계에 따른 독립 검토 정책은 아직 없습니다. 은행 송금, 송금 취소, 환불, 세금계산서 발급을 수행하지 않습니다. 지급 정정은 입력 오류를 바로잡는 것이며 실제 자금 이동을 취소하지 않습니다.

서버가 처리자와 시각을 기록하며 클라이언트의 임의 처리자 필드를 거부합니다. 기존 조직 revision 및 명령 idempotency를 재사용합니다. 입력 폼의 요청·지급 ID를 재시도 중 유지해 중복을 막습니다. 기존 `planned/confirmed/paid` 자료는 유지하며, 원장이 없는 과거 지급 완료는 기존 집행일·금액을 사용합니다. 과거에 존재하지 않은 처리자나 지급 시각을 만들어 넣지 않습니다.

업무 DB는 D1, 원본은 R2 그대로입니다. 이번 필드는 기존 조직 JSON의 선택적 확장이어서 D1 테이블 변경은 없습니다. 조직 JSON 1MiB 한도는 그대로이며, 1년 대량 운영을 위해 집행·지급·이력·보고서를 별도 테이블/스냅샷 저장으로 분리해야 합니다.

## 보고서 출력

- 화면·HTML·Word: 집행 명세, 기간 집행/지급과 미지급, 근거 버전. HTML/Word에는 지급 상세와 정정 사유도 포함합니다.
- Excel: 기존 성과 집계에 `집행 명세`, `지급 원장`, `집행 처리 이력` 시트를 추가합니다. 숫자는 숫자 셀로 유지하고 무효 지급도 구분해 보존합니다.
- 기존 저장 보고서는 그때의 내용을 그대로 유지합니다. 새 명세는 업데이트 이후 생성한 보고서에 들어갑니다.

## 검증과 남은 개발

66개 자동 검증 통과: 기존 문서·평가·조직·권한과 새 집행 도메인/서버 통합. 실제 브라우저의 예산 배정→요청→보완→수정→승인→부분 지급→월별 보고 연결, 예산 축소 차단 메시지, 모바일 가로 넘침을 확인했습니다. 실제 여러 사람이 동시에 사용한 운영 인수나 은행 거래 검증을 뜻하지 않습니다. 파일 출력의 Word 페이지별 시각 검증·OS 다운로드 인수 제한은 10 문서와 동일합니다.

후속 우선순위:

1. Google/Supabase 실제 인증 설정과 두 계정 인수, OpenAI 분석 키·모델 연결. 현재 외부 설정 대기 상태 유지.
2. 업무 댓글·언급·알림, 검토 담당자 지정, 다단계 결재와 독립 검토 정책.
3. 정산 기간·회계연도 이월·반납/환불·여러 재원 분담, 테이블 분리와 백업/복원·동시 사용 부하 검증.
4. OCR/STT/TTS·미분류함·문서 비교/복원·검색, 기관별 HWPX 서식·증빙 묶음.

전체 서비스의 운영 출시가 완료된 것으로 선언하지 않습니다. 최신 검증 결과는 `qa/verification.md`에 기록합니다.
